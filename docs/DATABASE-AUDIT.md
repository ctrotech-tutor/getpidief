# Database audit — first measured pass

## Scope and limits

This is a code/schema review plus an isolated synthetic PostgreSQL experiment, not an audit of the actual Supabase project. No hosted database, production statistics, production data, backup settings, or Supabase configuration were accessed or changed. The synthetic distribution and local hardware do not establish production latency, concurrency, percentiles, or capacity. Security is not certified by these checks. Do not run synthetic seed data or `EXPLAIN ANALYZE` experiments against production.

## Measured finding and change

The feed query used `feed_events` twice: to retrieve the page and to find a legacy ID-only cursor. PostgreSQL materialized the entire union in the observed plan, even for a 20-ID delivery. The cursor lookup now reads the original/repost primary key directly; filtering, ordering, block checks and interaction counts remain in place. This is a query-only change, with no new migration. The modern cursor supplies its own timestamp and continues to work after its boundary event is deleted; old ID-only cursors still require a surviving event. Saved does not resolve repost cursors.

On one local PostgreSQL 18.6 instance with warm buffers, after `ANALYZE`, one run of `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` used 1,000 synthetic accounts, 100,000 posts, 30,000 reposts, 100,000 replies, 100,000 likes, and 100 follows for the reader. Times below are server execution times for the main query, **not** end-to-end page load or a percentile. PostgreSQL version, statistics, indexes, parameters and data distributions affect plans.

| Read | Before | After | Notes |
| --- | ---: | ---: | --- |
| 20 specific originals (For you delivery) | 71.7 ms | 0.62 ms | Observed full 130,000-event materialization disappeared. |
| Latest first page | 388.9 ms | 37.0 ms | Still scans/sorts a large event set in this plan. |
| Following first page | 142.5 ms | 102.9 ms | Still filters/sorts many events; needs separate work. |
| Discovery candidates | 1.44 ms | 1.50 ms | Separate query, unchanged; timing variation is expected. |

A second reply-preview query ran in roughly 0.2–0.3 ms for the sampled pages. These are isolated samples with a simplistic distribution; no p50/p95/p99, contention, cold-cache, network, Supabase pooler or real-world measurements have been performed. The dataset had no blocks and minimal engagement per post; heavy-engagement and highly selective follow/block cases may behave differently. Additional metrics and database-level tests are required before calling the system production-scalable.

The feed PostgreSQL integration suite covers mixed post/repost timestamps, old and new cursors, deleted boundaries, block eligibility, interaction counts and reposts. The server-rendering tests now wait for Suspense boundaries to finish, rather than asserting against the loading fallback.

## Other concrete observations

- The Node process uses a `pg` pool of up to five connections. In serverless, this is **per process**, not a global five-connection limit; concurrent instances and background workers multiply demand. Supabase's transaction pooler is recommended for runtime, with a separately supplied session/direct connection for migration. Actual limits and deployed connection strings were not inspected. Instrument wait time, total and idle connections, timeouts, active instances, pooler queues and PostgreSQL connections before changing pool sizes. Do not log URLs or SQL parameters.
- In the migrated local schema, both `auth_users_email_unique` and `auth_users_email_idx` are unique btree indexes on `email`, and both `users_username_unique` and `users_username_idx` are unique btree indexes on `username`. They are duplicate definitions and impose write/storage overhead. `follows_follower_idx` also has the same leading column as the pair index, but is not identical and may have a different planner/storage tradeoff. Do not drop any until actual index usage, foreign-key/constraint dependencies, migration drift and rollback are reviewed. The constraint-backed unique indexes enforce integrity.
- Following and legacy chronological reads still sort or filter substantial parts of the event union in this experiment. For-you candidate ranking also computes viewer-specific reply counts; popular posts, many blocks and high follow counts may change its cost. Test first/deep pages, refresh by IDs, sparse/dense follows, blocked users, active/inactive authors and highly engaged posts before considering branch-specific top-N retrieval or carefully selected indexes. A top-N rewrite must filter eligibility **before** limiting and preserve exact `(timestamp, kind, id)` cursor semantics.
- Follow suggestions rank eligible users with per-candidate interest overlap and use offset paging. Notifications use offset plus an exact count, and search uses `COUNT(*) OVER()` and offset. These are potential high-cardinality costs, not measured bottlenecks here. Assess actual plans before designing keyset pagination, caching or approximate counts; preserve privacy and total-count semantics.
- Feed interactions acquire account and post row locks in a consistent order to serialize against blocks/deletions. That protects correctness, but a popular author or viewer can become a contention point. Measure concurrent interactions, lock wait times and deadlocks before weakening or replacing locking.
- Both indexes and per-post counts have write/read costs. Avoid speculative indexes, unbounded cache, denormalized counts or background fanout without benchmarks and a repair/reconciliation design. Existing feed safety/visibility checks must not be bypassed for speed.
- `db` enables query logging in development. SQL and parameters can contain user data: keep debug logs out of public logs and disable or redact in shared environments. Production query logging, slow-query collection, `pg_stat_statements`, and dashboard retention were not inspected.
- Check backup frequency, retention, point-in-time recovery availability, restore drills, migration ownership, RLS/Data API exposure, TLS and least privilege in the actual Supabase project. Code review cannot establish these. Use a separate staging database, representative anonymized or synthetic distribution, and reviewed migration/rollback plans. Never use production `db:push` or seed it with known-password demo users.

## Second pass: bounded timeline branches

The chronological query now retrieves at most 21 eligible, cursor-matching events **from each** of the original and repost streams before merging. All author/reposter status, block, follow/save and cursor conditions apply inside each branch before its limit; the existing outer checks remain. For fixed event kinds, the branch ordering by timestamp and ID is equivalent to the global `(timestamp, kind, id)` ordering, so no event in a branch below its first 21 eligible items can be in the global first 21. Specific-ID revalidation retains the separate unbounded-by-branch path. An empty-follow existence check avoids scanning the event tables when nobody is followed. No index or migration was added.

In a second local PostgreSQL 18.6 experiment using `scripts/bench/feed-database.ts`, with warm cache and ten serial application-level samples, approximate lower medians before/after (not a production benchmark) were:

| Scenario | Before | After |
| --- | ---: | ---: |
| Following, 100 followed accounts, including blocked/inactive authors | 83.27 ms | 4.92 ms |
| Following, one account | 49.41 ms | 9.97 ms |
| Following, no accounts | 15.46 ms | 3.98 ms |
| Following, deep cursor | 58.33 ms | 4.55 ms |
| Latest, first page | 31.08 ms | 5.59 ms |
| Saved, first page | 26.36 ms | 5.94 ms |
| For-you 20-ID delivery (unchanged path) | 4.94 ms | 4.82 ms |

Ten runs are insufficient to estimate reliable tail latency; the script's sample maximum is not a production p95. Its deterministic data has 1,000 accounts, 100k posts, 30k reposts, 100k replies and likes, 5k saves, a few blocks and inactive accounts. It does not model popular-post skew, high concurrency, realistic request rates, network latency, vacuum/dead tuples, cold disk, or Supabase. The people suggestion query measured ~2.19 ms lower median on that small dataset with no interests; it must not be extrapolated to a large or interest-rich user base. The original and revised feed results were compared on the same fixture for three viewers, all three views, first pages, precise and ID-only post/repost cursors; they matched. Dedicated integration coverage also exercises blocked originals/reposters above the branch limits and pagination ties.

### Reproducing locally

Use a **new, isolated, empty** local PostgreSQL database whose name ends in `_test`. Migrate that disposable database using the normal local process. Then, with `TEST_DATABASE_URL` set to its local URL, explicitly set `BENCH_WRITE=yes` and run `npx tsx scripts/bench/feed-database.ts --seed`. The seed is synthetic and deliberately refuses non-local targets, database names not ending `_test`, missing write confirmation, or occupied public tables; do not run it in a shared database. Run `npx tsx scripts/bench/feed-database.ts` with the same `TEST_DATABASE_URL` to measure reads. It uses warm-up runs, ten serial samples and `EXPLAIN (ANALYZE, BUFFERS)`; it does not report credentials or query parameters. The script checks hostname/name but cannot prove that a local database is disposable; the operator must verify the target. Stop and remove the test database afterward.

Still open: skewed/multi-million-row datasets, actual query-count and tail-latency profiling, contention, suggestions with many interests, search, notifications, pooled connection pressure and production configuration. Neither the speedup nor the current indexing strategy has been validated under production traffic. No production schema, settings or data were changed.

## Third pass: search and notifications

A further isolated PostgreSQL 18.6 experiment used 1,000 synthetic users, 100,000 resources, 100,000 notifications, 19 directional blocks, and a reader with 50,000 notifications (10,000 unread). It used warm buffers, five serial application-level samples per scenario, and `EXPLAIN (ANALYZE, BUFFERS)`; this is not a production benchmark, a concurrency test, or a reliable tail-latency estimate. The fixture has simple uniform titles, few blocks and no real traffic; rare/common selectivity and database hardware materially affect results.

Two changes were made without a schema migration:

- Search now calculates the exact visible total separately from the sorted page **within one SQL statement and snapshot**, avoiding the window count over wide result rows. A left join preserves the total on an out-of-range page. Every count still uses the same authorization, account, visibility and filter predicates as the page. An ID tie-breaker makes pagination deterministic for equal sort values. Approximate local medians: common term 264.2 → 125.1 ms; blank query 232.9 → 111.5 ms; page 100 for the common term 282.7 → 176.5 ms. A rare term was 14.2 → 14.8 ms in the same short run: doing two scans can be slower for selective queries. The result is not a guarantee that the new plan is always faster. Exact counting still scales with the number of matching visible resources; offsets remain expensive, and the additional scan increases buffer work.
- Viewer-specific resource and notification block filters use two equivalent directional `NOT EXISTS` checks rather than one `OR` within a correlated anti-check. NULL notification senders remain visible. The planner can use each directional block index or a hash anti-join. With the synthetic notification distribution, list (including exact count) measured 66.3 → 16.9 ms median and unread count 17.3 → 4.4 ms; performance depends on block and recipient distributions. PostgreSQL tests exercise blocks in both directions and senderless notices.

Search previously returned a total of zero for an out-of-range page even when earlier pages had matches. Regression tests cover this, all search sort options, equal sort values and blocked users. The notification API now rejects non-positive, malformed or unsafe page/limit values, page sizes above 100, offsets above 100,000, and unknown types before issuing queries; this intentionally caps extremely deep offset pagination. Cursor-based pagination would be a separate API/product change. No count caching was added, because visibility can change concurrently with a block.

To reproduce, migrate a **new, empty, isolated local `_test` database**, set `TEST_DATABASE_URL` and `BENCH_WRITE=yes`, then run `npx tsx scripts/bench/search-notifications.ts --seed`. Remove `BENCH_WRITE` and run the same script without `--seed` to measure. The script refuses non-local/non-`_test` URLs and non-empty public tables, and never prints SQL or parameters; the operator must still verify that the database is disposable. It generates artificial, non-user content and should never be run against shared or hosted data. Separate database fixtures are required from the feed benchmark. Production indexes, data, backup settings and Supabase configuration were not inspected or changed.

Remaining work includes more representative search relevance and institution distributions, read/write contention, page depths, high-block and high-engagement cases, cache-cold behavior, pool saturation and safe staging/production observations. Exact totals and offset pagination can remain expensive even with the improvements here; no claims of universal speed or production capacity are warranted.

## Fourth pass: interaction locks and pool pressure

The feed interaction transaction now takes `FOR SHARE` on involved account rows (in sorted ID order) and on the post, rather than `FOR UPDATE`. Independent likes, saves, replies and reposts can therefore overlap. These shared locks **still conflict** with the exclusive account locks used by block/follow operations and with account updates, post updates and deletion. The transaction rechecks blocks after acquiring account locks and rechecks the post under its lock. Report transactions retain their existing exclusive locks. Callbacks passed to `withPostInteraction` must not update the locked account or post rows or perform lock upgrades; current callbacks only write interaction rows. Unique constraints still enforce idempotent likes, saves and reposts. Concurrent opposing requests, especially across devices, have no guaranteed user-intent ordering; the UI only serializes its own in-flight control.

Disposable PostgreSQL tests verify two interactions on the same post can overlap, and both ordering directions for block and soft deletion: a change that holds its lock first is rechecked, while a change requested during an interaction waits. Account suspension and deduplication are also exercised. These tests do not establish that every block surface is complete; user-facing blocking remains paused. A shared-row-lock design can create PostgreSQL MultiXact/vacuum overhead under heavy concurrent use, so observe that under sustained load before rollout.

Three short local PostgreSQL 18.6 runs used 120 synthetic likes, five connections in one Node process, warm cache, and worker concurrency 5 or 20. With 20 workers targeting different posts from the same author, total batch times were 253.5–305.6 ms using exclusive locks and 183.1–220.0 ms using shared locks. Same-post batches were 211.6–234.7 ms versus 144.8–169.8 ms. Sampled database lock waiters peaked at 4 versus 0 in those cases, but **pool waiters still peaked at 15** at concurrency 20 in both cases. Sampled maxima can miss short waits. Results are local, small, short, and highly variable—not a production throughput or p95 claim. There was no network latency, Supabase pooler, multi-instance traffic, database contention from other workloads, or failure injection. All 120 synthetic inserts completed in each run.

For reproduction, migrate a **fresh empty local `_test` database**; with `TEST_DATABASE_URL` and `BENCH_WRITE=yes`, run `npx tsx scripts/bench/feed-concurrency.ts --seed`, then run the same command without `--seed`. The benchmark performs writes and deletes its synthetic like rows on each scenario. It refuses non-local/non-`_test` targets, requires explicit write confirmation and checks that the expected exclusive synthetic users and posts exist. Hostname/name and fixture checks are guardrails, not proof a database is disposable; never run against shared, hosted or real data. Monitoring samples `pg_stat_activity` lock wait types and the local pool's waiting count; it does not print query parameters or account IDs. Remove the test database afterward.

The runtime pool limit remains five **per Node process**, not five across Vercel instances. This experiment does not justify increasing it. Before changing capacity, measure request rates, queue wait duration, timeouts, active serverless instances, pooler utilization, database connection limits, lock waits and `pg_stat_activity`/MultiXact health in staging and production under appropriate permissions. The Supabase transaction pooler does not eliminate the total database/backend capacity constraint. No hosted database or settings were accessed or changed.

## Fifth pass: people recommendations

The follow-suggestion query previously recomputed shared-interest counts for every candidate. It now aggregates matching interests once and joins those counts, with separate directional block anti-checks. Institution priority, shared-interest count, follower count, ID tie-break, follow/block/account exclusions and offset pagination remain unchanged. No index or migration was added. The grouped join intentionally retains duplicate-row multiplicity, matching the previous scoring behavior rather than silently changing rankings.

On local PostgreSQL 18.6, a synthetic 50,000-user fixture with 250,000+ interest rows, 100 tags and warm buffers produced five serial-sample medians of 150.45 → 75.11 ms for five viewer interests and 97.93 → 33.44 ms for none. A stress viewer with 55 interests took approximately 23.95–24.78 seconds in two individual old-query calls versus 328.46 ms median in five new-query calls. This stress case exceeds the current onboarding selection limit of 20 and is not representative of normal onboarding. At offset 1,000, the new median was 114.63 ms; an old single sample was approximately 143 ms, not a comparable median. Old and new result rows matched for three viewers at offsets 0 and 1,000; an additional disposable PostgreSQL regression covers duplicate interests, both block directions, follows, suspended/incomplete accounts, institution priority and pagination. These short, serial, synthetic measurements do not establish production latency or tail performance. Aggregating popular tags still processes many matches, and deep offsets still require ranking candidates.

To reproduce, migrate a **fresh, empty, isolated local `_test` database**, set `TEST_DATABASE_URL` and `BENCH_WRITE=yes`, then run `npx tsx scripts/bench/people-recommendations.ts --seed`. Run without `--seed` for measurements; `BENCH_SCENARIO` optionally selects a printed scenario name. Guards reject non-local/non-`_test` targets and occupied public tables, but cannot prove the target is disposable. Never use hosted or shared data. No hosted configuration or data was inspected or modified.

Integrity concern: the initial migration did not create composite primary keys for `user_interests`, `document_tags`, or `document_course_codes`, despite schema declarations that appear to intend them. Thus duplicate associations are possible and `onConflictDoNothing` alone does not prevent duplicate document tags. No automatic cleanup or constraint was applied: safe remediation requires measuring existing duplicates, understanding write paths and concurrency, planning deduplication and a migration with appropriate locking/rollback on a staging copy. The SQL optimization deliberately does not assume this integrity issue is fixed.

## Sixth pass: association integrity and upload writes

The current migrated database does **not** enforce uniqueness for `user_interests (user_id, tag_id)`, `document_tags (document_id, tag_id)`, or `document_course_codes (document_id, course_code_id)`. The object-shaped `pk` entries in the Drizzle definitions are not primary-key declarations; the initial generated migration confirms no primary keys on those tables. `user_interests.tag_id` also has no foreign key in the migrated schema. These are database-wide integrity gaps, not merely query performance problems.

Mitigations that do not require a migration:

- The document upload transaction now resolves and deduplicates tag IDs and normalized tag names before inserting links. It sorts distinct slugs before upserts to give concurrent uploads a consistent tag-lock order. A real PostgreSQL test also exposed and fixed an existing ambiguous `usage_count` reference in the tag upsert, which could fail uploads containing tag names. The test verifies duplicate IDs, duplicate normalized names, and overlap between ID and name produce a single association. These changes apply to this upload path only; they do not protect arbitrary database writers.
- The legacy `usersRepository.updateInterests` replacement now locks the user profile row, like onboarding and interest settings, and deduplicates input before insertion. This serializes cooperating replacement writers; it does not prevent other writers from inserting duplicates without taking that lock. The concurrency test confirms the repository waits for another profile-locked writer and then replaces its complete selection.
- No existing associations are deleted and no automatic schema migration is included. Duplicate cleanup can change recommendation weighting and resource output. In `document_course_codes`, duplicate rows may disagree about `raw_code` or contain both null and non-null values, so a generic “keep one” policy risks data loss. The audit also does not establish whether production has any duplicates or orphans.

For an **isolated local copy only**, `TEST_DATABASE_URL=... npx tsx scripts/audit/association-integrity.ts` reports aggregate duplicate-group and excess-row counts, groups with conflicting/missing raw course code values, and interest rows whose tag is missing. The script accepts only local hosts and database names ending `_test`, uses a read-only repeatable-read transaction with a 30-second per-statement timeout, and prints no URLs or IDs. A local hostname/name does not guarantee isolation: the operator must verify the database and should avoid sensitive data in unprotected copies. It performs full grouping/scans, which can be expensive, can time out, and a long snapshot can delay vacuum; it is not suitable for running casually against production. It does not validate every foreign key, constraint, or application invariant.

Before enforcing uniqueness: agree on a data-retention/merge policy (especially `raw_code` and timestamps), inspect a suitably protected staging copy, verify backups and restore procedure, test application compatibility and duplicate cleanup, and plan operational lock/timeout and rollback steps with an owner. A production rollout needs an approved way to handle writes racing cleanup and index creation; concurrent unique index creation has different transaction/failed-index handling from normal transactional migrations. Verify actual catalog/index state and orphan policy first, and do not add a foreign key or remove indexes without a separate reviewed plan. Enforcing uniqueness will intentionally change old duplicate-weighted recommendation scores and requires updated tests. None of this has been applied to hosted data or settings.

## Seventh pass: Explore resource discovery

The prior recommendation query computed a relevance score but `DISTINCT ON (d.id)` forced ordering by ID before its limit, so it returned the lowest IDs rather than the highest scores. It also excluded an arbitrary 200 view rows (not necessarily 200 distinct or recent documents), and a cached array of hydrated cards was reused regardless of requested limit or later moderation/visibility changes. Trending hydration did not require public visibility. The Redis-empty trending fallback also dropped category, institution, and viewer arguments.

Recommendations now rank eligible public documents by existing `trending_score + 10 * matching document-tag rows`, with ID ascending for deterministic ties. Duplicate document-tag rows retain their previous score effect pending a deliberate integrity migration; duplicate viewer-interest rows do not multiply matches. All previously viewed documents are excluded, not just an arbitrary 200 rows, and the recommendation section may therefore be empty rather than falling back to already-viewed content. This is a deliberate behavior change; other Explore sections can still show viewed resources. We removed caching of recommendation cards so each request re-evaluates eligibility and its requested limit. A second hydration query rechecks public status, active author and viewer-specific blocks; a concurrent change can shorten the result. This does not provide a transactionally frozen result across the two statements, nor does it guarantee that a document viewed between ranking and hydration disappears from that response.

Explore's recommendation, trending and recent sections now apply active-author and bidirectional block filtering where a viewer is known. Trending Redis IDs are rehydrated against current public and author eligibility, and the empty-Redis fallback retains filters. The Redis list is limited before hydration, so stale/ineligible IDs can leave that section underfilled. Anonymous discovery has no viewer-specific block check. Other resource surfaces, including related resources and direct-resource policy, have not been comprehensively reviewed here; **blocking remains incomplete and hidden**, not a production guarantee.

A local PostgreSQL 18.6 synthetic fixture with 50,000 public documents, 150,000 document-tag rows, 101 users and 100 tags used warm buffers and five serial samples. The new full recommendation call including hydration had a median of 122.88 ms for a viewer with five interests and 500 views, and 108.56 ms with no interests or views. These are not speedup comparisons: the old query returned a different and incorrectly ordered set and could use stale cache. The new uncached query aggregates and ranks the eligible population on every request, so high concurrency, popular tags, large histories, cold buffers and network/pool wait can be costly. `EXPLAIN ANALYZE` samples were slower and are not directly comparable to the five application samples. No production performance or tail-latency claim is made; measure in staging before choosing safe candidate limits, indexes or an invalidation-aware cache.

For reproduction, migrate a new, empty, isolated local `_test` database, set `TEST_DATABASE_URL` and `BENCH_WRITE=yes`, then run `npx tsx scripts/bench/resource-discovery.ts --seed`; remove `BENCH_WRITE` and run without `--seed`. Guards reject non-local/non-`_test` targets, missing confirmation and occupied public tables, but cannot prove isolation. Never use shared or hosted data. Tests cover score order and ties, more than 200 viewed resources, both block directions, inactive/private/deleted resources, different limits, stale Redis trending IDs and hydration visibility. No hosted data or configuration was inspected or changed.

## Eighth pass: rollback-only uniqueness rehearsal

`scripts/audit/rehearse-association-uniqueness.ts` is an **experiment, not a migration**. It requires an explicitly confirmed loopback PostgreSQL URL ending in `_test` without URL parameters, sets a two-second lock timeout and a 30-second per-statement timeout, locks the three association tables against competing writes, rejects any duplicate course-code groups with different `raw_code` values (including null versus non-null), removes duplicate pairs within the transaction using earliest `created_at` with `ctid` as a tie-break, and attempts ordinary unique-index creation. It reports aggregate removed counts and a post-cleanup audit, then always rolls back both deletes and indexes, including on error. It does not add an interest/tag foreign key or resolve orphan data. `ctid` is only a transient tie-break for this experiment, not an identifier or approved production retention policy.

For a verified **disposable local test database only**, set `TEST_DATABASE_URL` and `ASSOCIATION_REHEARSAL_WRITE=yes`, then run `npx tsx scripts/audit/rehearse-association-uniqueness.ts`. The test URL and confirmation are guardrails, not proof that localhost is not a tunnel. This script issues DELETE and CREATE INDEX statements and obtains write-conflicting table locks even though its transaction is rolled back. It can block local writes, use significant CPU/disk/temp space, generate WAL and fail on timeouts; never aim it at a hosted, shared, or production database. If the process crashes or its connection closes, PostgreSQL rolls back the open transaction, but an operator should verify no session or locks remain. A successful rehearsal does not mean the data-cleanup policy, index creation procedure, concurrent-write handling, or rollback plan has been approved for production.

Disposable PostgreSQL tests cover duplicate preservation after rollback, absence of committed indexes, refusal of mixed raw values, explicit confirmation and target guardrails, and lock timeout with a competing writer. A production strategy still needs a protected representative staging copy, a retention decision for timestamps and raw codes, an orphan policy, backup and restore rehearsal, a safe online/maintenance plan and review of the effects on recommendation scores. No hosted data or settings were accessed.

## Ninth pass: bounded feed refresh and local-test target guards

Feed refresh requests can specify up to 140 post/repost event IDs to revalidate a discovery snapshot or previously loaded feed. The refresh query now restricts each event branch by its requested IDs **before** the union; this lets the planner use primary-key lookups without first evaluating a tuple filter over the combined event streams. The existing account, post, follow, save, block and cursor checks remain in place before delivery, and repeated keys retain set semantics. An empty internal key list returns an empty result rather than invalid SQL. This does not change chronological feed page queries or the incomplete status of blocking.

On isolated PostgreSQL 18.6 with the earlier synthetic 100,000 posts, 30,000 reposts, 100,000 replies and 100,000 likes, 20 warm serial samples per version were interleaved, including the two application queries for events and reply previews. Median old → new: 20 post IDs **5.35 → 4.97 ms**; 140 post IDs **12.08 → 10.61 ms**; 140 mixed IDs **23.57 → 17.06 ms**. This is a small local measurement, not a production or tail-latency guarantee. Planner choices, cursor depth, blocks, engagement skew, network, cache state and concurrency can change results. Ninety old/new cases matched on that fixture across Latest/Following/Saved, three viewers, post-only/repost-only/mixed/duplicate/missing IDs and cursor/no cursor. PostgreSQL regressions additionally cover both block directions, active-author state, saved/following filtering, an empty list and timestamp ordering. The benchmark now includes 140-key scenarios and labels its ten-sample maximum as a sample maximum, not a p95.

The benchmark and local audit scripts previously validated only the URL authority, although node-postgres can interpret query parameters such as `?host=...` as connection overrides. They now share a local-target guard which requires a PostgreSQL URL, loopback authority, `_test` database name and **no query string or fragment**; write-enabled Vitest setup applies the same check to `TEST_DATABASE_URL` and `TEST_SEED_DATABASE_URL`. Tests exercise remote hosts, host/socket overrides, fragments and unsupported schemes. This is a safety improvement, not proof of isolation: localhost may still be a tunnel or proxy, and operators must independently verify the actual server and database. Explicit write confirmations and fixture checks remain required. No hosted data or configuration was accessed.
