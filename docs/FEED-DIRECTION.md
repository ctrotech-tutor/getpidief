# Feed foundation and next phases

## Product direction

The signed-in root is the social home: people share thoughts and questions, discuss, save, and discover useful work. Resources belong in conversations, not just a catalogue. The default **For you** view uses a small explainable ranking and local viewed-post history; the legacy **Latest** URL is chronological. Following contains events by followed accounts in chronological order, and Saved contains the user's saved posts. Discovery is not a learned or topic-personalized model.

The first phase supplies a responsive feed shell, composer, post anatomy, discussion entry, truthful empty states, and existing resource-search and library access. The home view uses real data only. The existing /explore remains available: do not redirect or retire it before its resource discovery functionality has a tested replacement. Post detail and resource flows remain available and are not reimplemented here.

## Architecture and data decisions

- `auth_users` owns credentials and `users` is the existing one-to-one profile. Reuse identity, profile and `follows` rather than duplicating users or creating a separate feed identity. The follow pair has a unique index. Every read and mutation must continue to check active/deleted state and authorization.
- `posts` owns text and kind, while replies, likes and saves are separate records with foreign keys and uniqueness constraints. The current feed is bounded to 20 posts and reads two recent replies per post; it uses the indexed `(created_at, id)` order. New pagination links carry the original event timestamp at PostgreSQL microsecond precision together with event kind and ID, allowing pagination to continue if the cursor event is deleted. Legacy ID-only links still depend on resolving the event.
- Following uses an `EXISTS` lookup on follower and author, so it does not multiply posts by join rows. Existing indexes help but performance is workload-dependent: benchmark with realistic data and `EXPLAIN (ANALYZE, BUFFERS)` before adding an author/time partial index or fan-out infrastructure. No synthetic production data or unmeasured performance claims.
- A future topic association should be a join table with unique `(post_id, tag_id)`, reverse lookup `(tag_id, post_id)`, foreign keys and bounded active-topic selection validated server-side. Plan migrations, existing-post behavior, tag moderation and transactional writes before shipping it. Do not infer sensitive categories from free text.
- A future PDF association should refer to the canonical document record, not copy a file URL into a post. Specify author ownership, status, visibility and authorization at creation and every read; withheld, deleted or inaccessible documents must never leak through cards or signed URLs. Existing UploadThing privacy requires live verification before private delivery is enabled.
- For you selects up to 120 eligible recent original posts, scores recency, follows and bounded visible discussion activity, and spreads adjacent authors. The browser holds an ordered snapshot for pagination and fetches each batch through the existing viewer-filtered read, so removals and blocks are rechecked. Reopening prefers unseen IDs remembered locally on that device. This is a heuristic, not a learned model; ranking quality and database performance have not been benchmarked.
- Viewed history stores at most 300 post IDs and timestamps per account in browser localStorage, used for seven days after at least 1.5 seconds at 50% visibility in a visible tab. It is not sent as a history list to the server, is not cross-device, and users can clear it in Privacy settings. Expired entries are ignored and are pruned on a later write; local storage can remain on a shared device until cleared. The feature has not undergone a formal privacy review. No sensitive inference or engagement-only optimization.

## Delivery and verification

The first feed batch is server-rendered. Further batches append as the reader scrolls; automatic loading can be paused via a keyboard-accessible control, and data-saving connections start with automatic loading off. The Load more control appears when focused, after errors, when automatic loading is unavailable or paused, or when the retained-item limit is reached. A non-JavaScript navigation fallback remains for chronological feeds. Loading uses post skeletons and a screen-reader announcement. When the first batch refreshes, appended events are rechecked for current visibility and interaction state rather than discarded; inaccessible events are removed. Appended events are temporarily hidden during this check. The stream limits retained extra items and provides a continuation link at the limit. For you also restores a bounded, account-scoped ID-only snapshot when returning from a post, rechecking eligibility before display; Latest and Following scroll restoration and real-browser/accessibility verification remain. An unpublished post stays in the editor after an error; closing a non-empty editor asks to discard or keep writing. There is no persistent drafts feature yet, so navigation or refresh can lose unfinished text. New feed posts are limited to 280 Unicode code points on both client and server; existing longer posts are unchanged. Production safety behavior, abuse limits, report/review paths and row visibility remain in force.

Next phases: topic-aware posts and candidate ranking; real follow/discovery controls and people search; PDF attachments; richer conversation and actions; safe consolidation of /explore. Browser-test mobile, keyboard, screen reader, zoom and slow connections, and measure real latency and interaction performance before making performance claims. Existing resource search is resource-focused, not yet people/post search.
