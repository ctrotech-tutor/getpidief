# Reposts and blocking: implementation groundwork

**Status: reposts implemented for local testing; blocking is partially implemented but not exposed or complete.** The migration is additive, but should be reviewed with the complete feature before being applied to a shared or production database. No production migration or seed is part of this work.

## Reposts

`post_reposts` stores an attributed event pointing to an original post, rather than duplicating the body. A user can have at most one active repost of the same original; deleting the repost leaves the original untouched. Hard deletion of either the original or the reposting user cascades to the event.

Current behavior: an authenticated, active user can repost or undo a repost with an idempotent server action. The original post is never copied. Latest shows both original and attributed repost events; Following includes events by followed accounts; Saved shows original posts only. Pagination uses the event timestamp, type and ID in PostgreSQL. Inactive actors and removed originals are hidden. Creation uses the feed posting rate limit. A removed cursor may end pagination, as with the previous feed cursor.

Remaining work: apply eventual blocking rules to originals, actors, counts and write paths; exercise the UI and rate-limiter failure cases in a browser; review event query performance with realistic production data and check concurrent account moderation. Reposting is not a quote post, does not provide notifications, and does not imply public unauthenticated access.

## Blocking

`user_blocks` is a directional relationship: `blocker_id` created the block against `blocked_id`. A database constraint rejects self-blocks; duplicate pairs are unique; deleting either account cascades. An internal repository can insert/remove blocks and atomically removes mutual follows; unblock takes matching account locks and may remove a block against a suspended or soft-deleted account. The internal outgoing-block list uses ID-cursor pagination and masks unavailable account details; it is not an authenticated endpoint, so future callers must authorize the owner themselves. New follows check both directions under matching account locks. Feed event reads, reply previews/counts, direct discussion reads, viewer-aware profile reads and metadata, and initial feed-action target validation now filter blocked pairs. Direct-ID reports of a blocked reply are also rejected. No Block or Unblock control or authenticated API is exposed yet.

Before exposing the action, design and implement:

- Add authorized, rate-limited actions, a clear confirmation and a reachable list of blocked accounts with unblock. The internal block operation removes follows in both directions and adjusts counts; unblock does not restore follows. Existing notification rows are retained; visible unread items remain unread if hidden and can reappear on unblock.
- Finish server-side checks across remaining APIs, search and other interactions; profile reads through `getPublicProfile` now check the signed-in viewer. Feed queries and follow creation have initial checks, but are not a complete safety boundary; like, save, reply and repost lock the account pair, re-check blocks after locking, and lock the original post before writing. Reporting similarly locks the reporter, post author and reply author in account-ID order, re-checks blocks, then locks the post and reply. Existing interactions are not erased when a block is created. Filtering is applied before feed pagination and visible reply/repost counts.
- Explicit treatment of resources, search, notification delivery and public/unauthenticated pages. The app currently has public content and some public file URLs: do **not** imply that a block makes such content private or prevents a logged-out visitor from accessing it.
- Audit existing direct write endpoints, author/account status and stale sessions; define reporting/moderation exceptions. Prevent bypass through APIs or a client-supplied ID, and test race conditions.
- Accessible confirmations, errors, repeat actions, unblock, and browser tests. Never silently claim a block succeeded if only one view has been filtered.

Notification page, list API and unread count now exclude senders blocked in either direction before pagination and counting; senderless notices remain visible. Mark-all-read affects only visible notices. Unread counts bypass Redis because block/unblock and asynchronous cache writes can race. The Inngest worker serializes insertion against blocks, and checks current account/block state immediately before realtime, email and push delivery. Realtime carries only a refresh signal; the `useNotifications` hook fetches the filtered count on receipt, but it is currently not mounted anywhere, so live badge updates are not established by this change. Email and push remain best-effort: a block can commit between the check and provider acceptance, and already delivered messages cannot be recalled. Inngest retries/memoized steps, stale client state and other notification producers also need a complete policy before exposing Block. Weekly digest content is compiled within the send step using current opt-in, address, follows and bidirectional block state; only active authors and approved public non-deleted resources are included before limits. It still has the external-provider race and cannot recall sent mail. Public Pulse uses a shared Pusher channel containing actor and document details, so it cannot filter per viewer; its polling API is also not block-aware. Both require a viewer-aware redesign before exposing Block. A sender deleted from the database becomes null, so its historical notification is treated as senderless.

Discovery: follower/following repository lists require an explicit viewer and filter both the list owner and entries before pagination and counts; follow suggestions exclude blocked accounts in either direction. Anonymous reads remain public. Audit other discovery paths before exposing Block. Resource search and autocomplete are not block-aware; document detail/download/file endpoints use publication and file policies, not a block relationship. Public resources and existing public URLs cannot be made private by a social block, including for logged-out users. Establish a consistent resource policy before changing those paths.

## Testing the groundwork

Against an **isolated, local, disposable** PostgreSQL database whose name ends in `_test`, run migrations and then:

```sh
TEST_DATABASE_URL=... TEST_DATABASE_WRITE=yes npx vitest --run tests/integration/postgres-feed-foundations.test.ts
```

Also run `tests/integration/postgres-weekly-digest.test.ts`, `tests/integration/postgres-block-management.test.ts`, `tests/integration/postgres-notification-delivery.test.ts`, `tests/integration/postgres-discovery-visibility.test.ts`, `tests/integration/postgres-notification-visibility.test.ts`, `tests/integration/postgres-block-repository.test.ts`, `tests/integration/postgres-interaction-locks.test.ts`, `tests/integration/postgres-report-locks.test.ts` and `tests/integration/postgres-feed.test.ts` with the same guarded environment. The guard in this test checks for a local hostname and database name suffix, but cannot detect a local tunnel to a remote database. The test creates and removes its own fixtures. Passing it verifies constraints only, not the finished product or security behavior.
