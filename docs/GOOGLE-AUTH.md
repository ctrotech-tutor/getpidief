# Google sign-in setup and verification

Google sign-in uses Auth.js OpenID Connect, with only the default identity scopes. It does not request offline access or retain Google API tokens. Google must report a verified email; an existing password account is **not** automatically linked by matching email. Sign in with the original method instead. There is currently no dedicated account-linking UI. Auth.js owns the OAuth state/PKCE checks and callback validation.

## Google Cloud configuration

1. In Google Cloud, select the intended project and configure Google Auth Platform: Branding, Audience and Data Access. Use the real app name, support contact, public homepage and privacy policy. Add and verify authorized domains as Google requires. Upload `public/google-oauth-logo.png` (120 × 120 PNG, well below 1 MB) as the app logo. Branding verification and publication may be required; an upload alone does not publish the logo. See [Google branding setup](https://support.google.com/cloud/answer/15549049) and [brand verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification).
2. Create a **Web application** OAuth client. Register the exact redirect URI for each intended deployment: `https://YOUR-DOMAIN/api/auth/callback/google` (for local development, `http://localhost:3000/api/auth/callback/google` if that is the actual origin). Exact scheme, host, port and path matter. Do not use a literal placeholder in the console. Preview hosts need their own registered callback or a separately configured OAuth redirect proxy; do not assume arbitrary previews work.
3. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `AUTH_SECRET`, `DATABASE_URL`, and the correct trusted application URL in the deployment environment. Keep secrets server-side and separate production from development. Restart after changes. Restrict external apps in Testing to configured test users until publication. Follow the provider and environment guidance at [Auth.js Google](https://authjs.dev/getting-started/providers/google) and [Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server).
4. Test with real credentials in the target environment: first sign-up, onboarding, return login, cancellation, an unverified Google email, suspended/deleted user, and a Google email matching an existing password account. Confirm callbacks and cookie behavior on the real domain. Review Google consent screen, branding verification status and policy URLs before production.

## Known limitations

The Google entry point explains that it creates an account and links to policies, but unlike password registration it does not record explicit, versioned acceptance in `account_agreements`. Legal/product review and a dedicated acceptance flow are needed if affirmative consent records are required. OAuth accounts have Auth.js `emailVerified = null`; Google verification is checked on each Google sign-in, not represented as email-provider verification. Do not enable automatic email linking. Identity and profile creation are transactional, but OAuth account linking happens afterward in Auth.js; an interrupted linking step can leave an unlinked identity that needs manual repair. Existing stored Google tokens, if any, are not purged by this change. Review existing OAuth grants and revoke/delete tokens as appropriate.
